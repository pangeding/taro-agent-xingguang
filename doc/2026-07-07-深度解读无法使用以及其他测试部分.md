## 解决方案

### Bug 根因分析

前端请求路径 **没有错**。问题出在 Go 后端 `POST /api/v1/readings/` 的实现遗漏了 AI 解读逻辑。

对比 Python 原版 (`backend/app/service/reading_service.py`)：
- `create_reading` (对应 `POST /readings/`)：**逐张调用 `interpret_card` 生成 AI 解读**
- `create_reading_langgraph` (对应 `POST /readings/langgraph`)：调用 LangGraph 编排生成解读

而 Go 版 `CreateReading` 方法中，原代码错误地直接返回了 fallback，未调用 LLM。

### 修复方案

修改 `internal/service/reading_service.go` 中的 `CreateReading` 方法，加入 LLM 调用逻辑。

### 修改文件

- `backend-go/internal/service/reading_service.go`

### 具体修改逻辑

**现状** (第 135 行)：
```go
rc.Interpretation = agent.GetBasicInterpretation(card, rc.IsReversed)
```

**修改为**：
```go
if s.LLM != nil {
    prompt := agent.BuildCardPrompt(card, rc.IsReversed, question, rc.Position, spreadType)
    text, err := s.LLM.Chat(context.Background(), agent.SYSTEM_PROMPT, prompt)
    if err != nil {
        rc.Interpretation = agent.GetBasicInterpretation(card, rc.IsReversed)
    } else {
        rc.Interpretation = text
    }
} else {
    rc.Interpretation = agent.GetBasicInterpretation(card, rc.IsReversed)
}
```

### 预期效果
- 请求 `POST /api/v1/readings/` 时，后端逐张调用 LLM 生成个性化解读
- 若 LLM 失败或 Key 未配置，降级返回基础解读
- 与 Python 版 `create_reading` 行为保持一致
