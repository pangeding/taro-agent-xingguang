## 1. 现状审计（带证据）

### 1.1 当前身份机制

**没有用户表，没有密码，没有登录。** 身份 = 浏览器 Cookie 里的一个 UUID。

链路：

1. 前端首次进页面调 `POST /api/v1/user/init`（`frontend/app/page.jsx:68`、`frontend/app/chat/page.jsx:75`）。
2. `handler.InitUser()`（`backend-go/internal/handler/user.go:8-20`）：若 `c.GetString("user_id")` 非空则原样返回，否则 `uuid.New()` 并 `c.SetCookie("user_id", ...)`。
3. `middleware.UserID()`（`backend-go/internal/middleware/user.go:7-22`）从 `X-User-Id` 头或 `user_id` Cookie 取值，`c.Set("user_id", userID)`。
4. 业务层以该字符串作为归属键，例如 `CreateConversation(userID, channel)`（`conversation_service.go:264-266`）。

已确认事实：

- `middleware.RequireUserID()`（`middleware/user.go:24-34`）**存在但从未注册**，`cmd/server/main.go:78` 只挂了 `middleware.UserID()`。属死代码。
- 前端**从不发送** `X-User-Id` 头（`grep` 全仓 0 命中），完全依赖 Cookie。
- Cookie 属性：`SetCookie("user_id", v, 1年, "/", "", secure=false, httpOnly=true)` —— `Secure` 恒为 `false`，且未调用 `c.SetSameSite`。
- 认证边界 = 「能伪造一个 `X-User-Id` 头就能冒充任何人」。当前 `CORS` 允许头里就包含 `X-User-Id`（`middleware/cors.go:12`）。

## 3. 设计决策

### 3.1 为什么是「Session 表 + Cookie」，不是 JWT

决定因素是本项目已有的两个硬约束，而不是偏好：

1. **`WS /api/v1/readings/ws` 存在**（`main.go:91`）。浏览器 `WebSocket` 构造函数**无法自定义请求头**，Cookie 会被自动携带，而 `Authorization: Bearer` 方案只能退化成 `?token=` 查询参数（会进日志、进 Referer）。Cookie Session 在这里是唯一优雅解。
2. **前端与后端同源**。`frontend/next.config.js:13-20` 有 `/api/:path*` → `http://localhost:8000/api/:path*` 的 rewrite，前端所有请求走 `credentials: 'same-origin'`（`lib/api.js:27`、`lib/sse.js:45`）。同源下 Cookie 无跨站障碍，也不需要 CORS 带凭证。

在此之上，Session 表还额外白拿两个能力，而 JWT 做这两个都要额外机制：

- **即时吊销**：改密/禁用账号 → 直接删行，下一个请求立即失效。
- **生产保护**：`must_change_password` 是「按请求生效」的状态（§3.3），天然需要每次请求读一次用户状态。既然要读，JWT 的「免 DB 查询」优势就不存在了。

代价：每请求一次 DB 查询（session + user 可一次 JOIN 取回）。单实例本地生产，可忽略。

**Token 规格**

- 生成：`crypto/rand` 32 字节 → `base64.RawURLEncoding`（43 字符）。
- 存储：DB 只存 `sha256(token)` 的 hex（64 字符）。**绝不存明文 token**——库被拖走也换不出可用会话。
- 下发：`c.SetSameSite(http.SameSiteLaxMode)` 后 `c.SetCookie(cfg.SessionCookieName, token, ttl, "/", "", cfg.CookieSecure, true)`。
  - 注意：Go 的 `c.SetCookie` **不会**设置 `SameSite`，必须单独调 `c.SetSameSite`。这是当前代码 `handler/user.go:17` 的既有缺陷，新代码不要重蹈。
  - `CookieSecure` 默认值 = `APP_ENV == "prod"`，可被 `COOKIE_SECURE` 覆盖（本地 http 起 prod 调试时需要）。

### 3.2 为什么新增 `owner_id` 而不是改 `conversations.user_id` 的类型

`conversations.user_id` 是 `varchar(100)`，装的是 UUID 字符串；目标是 `bigint unsigned` 外键。这条路在 MySQL 上会炸：

- GORM `AutoMigrate` **不会**把 `varchar` 改成 `bigint`（它只加列/加索引，不改列类型）。
- 手写 `ALTER TABLE conversations MODIFY user_id BIGINT UNSIGNED` 会把 29 个 UUID 全部隐式转成 `0`（非严格模式）或直接报错（严格模式），**数据不可逆丢失**。

改为**纯增量**：新增 `owner_id bigint unsigned NOT NULL DEFAULT 0` + 索引 → 回填 → 校验 → 老列单独一步删除。好处：

- 全程可回滚（老列还在，`DROP` 是最后一步且可延后一个 commit）。
- 回填前后行数可对账。
- 不依赖 MySQL 的隐式类型转换行为。

### 3.3 生产环境保护（三层，全部 fail-closed）

新增配置：

```bash
APP_ENV=dev                     # dev | prod，默认 dev
BOOTSTRAP_ADMIN_USERNAME=       # dev 默认 "admin"；prod 必填且禁止保留字
BOOTSTRAP_ADMIN_PASSWORD=       # dev 默认 "123456"；prod 必填且强度校验
SESSION_COOKIE_NAME=tarot_session
SESSION_TTL_HOURS=720           # 30 天
COOKIE_SECURE=                  # 留空 = (APP_ENV=="prod")
BIND_ADDR=                      # 留空 = (APP_ENV=="prod" ? "127.0.0.1:8000" : ":8000")
```

启动流程 `service.BootstrapUsers(db, cfg)`，在 `cmd/server/main.go` 的 `db.AutoMigrate` 之后、`r.Run` 之前调用：

**L1 — 引导账号校验（仅当 `users` 表为空）**

| `APP_ENV` | 行为 |
|---|---|
| `dev` | `users` 空 → 建 `admin` / `123456`，`role=admin`，`must_change_password=false`。验收：`git clone` 后 `go run cmd/server/main.go`，浏览器直接 `admin`/`123456` 登录成功。 |
| `prod` | `BOOTSTRAP_ADMIN_USERNAME` / `BOOTSTRAP_ADMIN_PASSWORD` 任一为空 → `log.Fatalf`。用户名命中保留字（`admin`/`root`/`administrator`/`test`/`guest`/`user`）→ `log.Fatalf`。密码不满足强度（长度 < 12，或全同字符，或等于用户名，或命中弱口令表）→ `log.Fatalf`。 |

**L2 — 存量口令扫描（每次启动，`APP_ENV=prod`）**

对 `users` 表中每个 `status=1` 的用户，用 `bcrypt.CompareHashAndPassword` 逐个比对内置弱口令表：

```
123456, 12345678, 123456789, 1234567890, password, admin, admin123,
qwerty, 111111, 000000, abc123, iloveyou, root, test, 123123
```

命中 → `log.Fatalf("检测到默认/弱口令用户 %q，拒绝在生产环境启动；请先执行 scripts/admin_user 重置口令")`。

> 这条是**关键保险**：即使运维图省事把 dev 的库直接搬到 prod，也会被拦下。`bcrypt` 比对是常数时间且必须逐条做（无法反查），用户量在个位数，启动开销可忽略。

**L3 — 强制改密门禁（按请求生效，`APP_ENV=prod` 且 `must_change_password=true`）**

`middleware.Auth()` 中，认证通过但 `must_change_password=true` 时：

- 放行 `POST /api/v1/auth/password`、`POST /api/v1/auth/logout`、`GET /api/v1/auth/me`。
- 其余 `/api/v1/*` 一律返回 `403 {"error":"password_change_required"}`。

不做「拒绝启动」，因为那会造成死锁：库里有弱口令 → 起不来 → 改不了密码 → 永远起不来。改为**能启动但业务不可用**，配合前端强制跳转到改密页，是自愈的。

配套运维 CLI（解决 L1/L2 触发后的现场处置，同时覆盖 TODO 16）：

```
go run scripts/admin_user/main.go list
go run scripts/admin_user/main.go create   --username <u> --password <p> --role admin|user
go run scripts/admin_user/main.go reset-password --username <u> --password <p>
go run scripts/admin_user/main.go rename  --from <old> --to <new>
go run scripts/admin_user/main.go disable --username <u>
```

CLI 直连数据库，**不受 `APP_ENV=prod` 的 L1/L2 拦截**（它不启动 HTTP 服务），所以是逃生通道。

**附**：`BIND_ADDR` 在 prod 默认绑 `127.0.0.1:8000`。当前 `main.go:106` 硬编码 `r.Run(":8000")` 监听所有网卡——本地生产若直连公网，等于把无 TLS 的后端暴露。生产应由 nginx 做 TLS 终止并反代到 127.0.0.1。

### 3.4 隔离的执行位置

**双层，服务层是权威，中间件只负责身份。**

- 中间件 `Auth()` 只做「你是谁」，把 `Actor` 放进 gin context。
- **每一个**带归属的查询都必须在服务层带归属条件。中间件层做不了这件事，因为它不知道哪条 SQL 触及了谁的数据。

新增 `backend-go/internal/auth/actor.go`：

```go
package auth

const (
    RoleUser  = "user"
    RoleAdmin = "admin"
)

// Actor 是本次请求的调用者。All 只在「管理员 + 显式 scope=all」时为 true。
type Actor struct {
    UserID uint
    Role   string
    All    bool
}

func (a Actor) IsAdmin() bool { return a.Role == RoleAdmin }

// VisibleTo 给查询加上归属过滤。col 是目标表的归属列名（如 "owner_id"）。
// 规则：默认只可见自己的数据；仅当 Role==admin 且 All==true 时才不过滤。
func (a Actor) VisibleTo(q *gorm.DB, col string) *gorm.DB {
    if a.IsAdmin() && a.All {
        return q
    }
    return q.Where(col+" = ?", a.UserID)
}
```

**核心设计原则：管理员默认只看到自己的数据。** 「能看全部」必须由请求显式声明 `?scope=all`。

反例（必须避免）：`if user.Role == "admin" { /* 不加过滤 */ }` 这种写法会让管理员在正常浏览自己的历史时看到全站数据，是数据泄露的常见来源，也让前端无法区分「我的」和「全部」。

### 3.5 越权返回码

非本人资源一律返回 **404 `{"error":"占卜记录不存在"}`**，不返回 403。

原因：403 会确认「该 ID 存在但不属于你」，把主键空间变成可枚举的存在性预言机。404 不泄露存在性。

## 4. 数据模型

### 4.1 新增表 `users`

```go
type User struct {
    ID                 uint       `gorm:"primaryKey;autoIncrement" json:"id"`
    Username           string     `gorm:"size:50;uniqueIndex;not null" json:"username"`
    PasswordHash       string     `gorm:"size:100;not null" json:"-"`
    DisplayName        string     `gorm:"size:50" json:"display_name"`
    Role               string     `gorm:"size:20;not null;default:user" json:"role"`      // user | admin
    Status             int8       `gorm:"not null;default:1" json:"status"`               // 1 启用 / 0 禁用
    MustChangePassword bool       `gorm:"not null;default:false" json:"must_change_password"`
    FailedAttempts     int        `gorm:"not null;default:0" json:"-"`
    LockedUntil        *time.Time `json:"-"`
    LastLoginAt        *time.Time `json:"last_login_at"`
    CreatedAt          time.Time  `gorm:"autoCreateTime" json:"created_at"`
    UpdatedAt          time.Time  `gorm:"autoCreateTime;autoUpdateTime" json:"updated_at"`
}

func (User) TableName() string { return "users" }
```

JSON 里 `password_hash` / `failed_attempts` / `locked_until` 必须 `json:"-"`，防止任何 handler 误序列化。

唯一索引加在 `username`。用户名规范化：入库前 `strings.ToLower(strings.TrimSpace(...))`，且只允许 `[a-z0-9_.-]{3,50}`——否则 `Admin` 与 `admin` 会同时存在，绕过 L1 的保留字检查。

### 4.2 新增表 `sessions`

```go
type Session struct {
    ID        uint      `gorm:"primaryKey;autoIncrement"`
    TokenHash string    `gorm:"size:64;uniqueIndex;not null"` // sha256 hex
    UserID    uint      `gorm:"index;not null"`
    ExpiresAt time.Time `gorm:"index;not null"`
    UserAgent string    `gorm:"size:255"`
    IP        string    `gorm:"size:64"`
    CreatedAt time.Time `gorm:"autoCreateTime"`
}

func (Session) TableName() string { return "sessions" }
```

不加外键约束（延续 `database.go:27` 的 `DisableForeignKeyConstraintWhenMigrating: true` 现状），靠代码保证一致性；用户删除时显式 `DELETE FROM sessions WHERE user_id = ?`。

### 4.3 归属列改造

| 表 | 新增列 | 说明 |
|---|---|---|
| `conversations` | `owner_id bigint unsigned NOT NULL DEFAULT 0` + `index` | 替代 `user_id varchar(100)` |
| `readings` | `owner_id bigint unsigned NOT NULL DEFAULT 0` + `index` | **全新**，此前无归属 |
| `readings` | `conversation_id bigint unsigned NULL` + `index` | 可选增强，见 §4.4 |
| `feedbacks` | `owner_id bigint unsigned NOT NULL DEFAULT 0` + `index` | 当前 0 行且无代码，仅保持结构一致 |

`messages` / `reading_cards` 不直接加 `owner_id`，它们通过 `conversation_id` / `reading_id` 归属。但**查询必须经父表校验**（见 §6.3 M6），否则 `GET /conversations/:id/messages` 换个 ID 就能读别人消息。

### 4.4 可选增强：`readings.conversation_id`

现状是用 `session_id = 'conv_<id>'` 这个字符串约定在反推关联，脆弱且已被前端重复实现一遍（`frontend/components/ReadingHistory.jsx:15-42` 靠「消息流里 `type=reading` 的 user 消息后跟带 `reading_id` 的 assistant 消息」来配对）。

加一个真实外键列可以让这个配对变成一次 JOIN。迁移可回填 45/60 行（已验证全部可解析）。

## 5. 数据迁移

新增一次性脚本 `backend-go/scripts/migrate_user_system/main.go`，**幂等**，支持 `DRY_RUN=1` 只打印不写。

### 5.1 前置事实（已 SQL 验证）

- `conversations`：41 行，29 个不同 `user_id`（全是浏览器 UUID，**没有任何一个是真实用户**）。
- `readings`：60 行，其中 45 行 `session_id` 形如 `conv_<N>` 且 **45/45 全部能反解到存在的 conversation**；15 行为随机 UUID，无任何归属线索。
- `readings.session_id` ∩ `conversations.user_id` = **0**。
- `messages`：111 行，38 行带 `reading_id`。
- `feedbacks`：0 行。

### 5.2 迁移原则

> 全部历史数据 → `admin`。

因为 29 个 UUID 是匿名的浏览器指纹，**无法也不应该**映射成 29 个用户（那会凭空造出 29 个无密码账号）。用户已明确要求「现有数据迁移到admin下」。

### 5.3 步骤（严格按序）

```
S1  建表：AutoMigrate(&User{}, &Session{})          // GORM 建新表，安全
S2  确保 admin 存在：不存在则按 §3.3 L1 的 dev 规则创建（admin/123456）
S3  加列：conversations.owner_id / readings.owner_id / readings.conversation_id / feedbacks.owner_id
     - 逐列查 information_schema.columns 判存在，已存在则跳过（幂等）
     - 用 raw DDL，不用 AutoMigrate（避免它对存量表做意外改动）
S4  回填 conversations：
       UPDATE conversations SET owner_id = <adminID> WHERE owner_id = 0
S5  回填 readings.conversation_id（若启用 §4.4）：
       UPDATE readings r
         JOIN conversations c ON r.session_id COLLATE utf8mb4_0900_ai_ci = CONCAT('conv_', c.id)
          SET r.conversation_id = c.id
        WHERE r.session_id REGEXP '^conv_[0-9]+$'
          AND (r.conversation_id IS NULL OR r.conversation_id = 0)
S6  回填 readings.owner_id：
       先按会话归属：UPDATE readings r JOIN conversations c ON c.id = r.conversation_id
                      SET r.owner_id = c.owner_id WHERE r.owner_id = 0 AND r.conversation_id IS NOT NULL
       剩余（孤儿）归 admin：UPDATE readings SET owner_id = <adminID> WHERE owner_id = 0
S7  回填 feedbacks.owner_id：经 reading_id 关联 readings.owner_id，取不到则 admin
S8  校验（不通过则 log.Fatalf，绝不静默继续）：
       - conversations 中 owner_id = 0 的行数 == 0
       - readings      中 owner_id = 0 的行数 == 0
       - 各表总行数 == 迁移前快照行数（conversations 41 / readings 60 / messages 111 / reading_cards 102）
       - readings.conversation_id 非空行数 == 45（若启用 §4.4）
S9  删老列（仅在 --drop-legacy 时执行）：
       ALTER TABLE conversations DROP COLUMN user_id;
```

### 5.4 必须注意的坑（都已在真库上踩到）

1. **collation 不一致**：`conversations.user_id`/`id` 是 `utf8mb4_0900_ai_ci`，`readings.session_id` 是 `utf8mb4_unicode_ci`。两者做 `=` 或 `JOIN` 会直接报错：
   `ERROR 1267 (HY000): Illegal mix of collations`。
   S5 的 JOIN 必须显式 `COLLATE utf8mb4_0900_ai_ci`（本次审计时就是这么绕过去的）。**不要**靠改表 collation 来规避——那会重写全表并影响其他列。
2. **`REGEXP '^conv_[0-9]+$'` 不能省**。若只写 `LIKE 'conv\_%'`，`CAST` 到 `UNSIGNED` 在 MySQL 8 严格模式下会告警/截断，产生 `conversation_id = 0` 的脏行。
3. **`SESSION_ID` 时序**：S4 必须在 S6 之前，否则 S6 按会话归属时读到的还是 `owner_id = 0`。
4. **SQLite 不覆盖**：`data/tarot.db` 已确认 `conversations` 为 0 行（是历史回退库，无业务数据）。脚本检测到 `driver != "mysql"` 时只执行 S1/S2 后退出，并打印说明。参考 `scripts/migrate_sqlite_to_mysql/main.go:22-25` 的既有做法。
5. **先在副本上跑**。建议 `mysqldump tarot > backup_$(date +%F).sql` 之后再执行；`DRY_RUN=1` 先看一遍 SQL。
6. **执行顺序**：迁移脚本必须**在部署带 Auth 中间件的新后端之前**跑完。否则新代码按 `owner_id` 过滤，而列还没回填 → 所有用户看到 0 条历史。

## 13. 实施记录：与原计划的偏差

本节记录编码阶段的实际决定，与原设计不同的地方都已在此说明原因。

### 13.1 结构调整

| 原计划 | 实际 | 原因 |
|---|---|---|
| `service.BootstrapUsers(d, cfg)` | **`internal/bootstrap` 包**的 `bootstrap.Users(d, cfg)` | 放 service 会让 `scripts/migrate_user_system` 与 `scripts/admin_user` 连带引入 `agent` → eino 一大串依赖。独立包只依赖 db/auth/config |
| `internal/middleware/auth.go` 直接依赖 `service.UserService` | 依赖 `middleware.SessionResolver` 接口 | 避免 middleware ↔ service 耦合成环，也便于测试注入 |
| 认证哨兵错误写在 service | **`internal/auth/errors.go`** | 原计划 middleware 与 service 各声明一份 `ErrAccountDisabled`，`errors.Is` 会永远不匹配 |

### 13.2 新增的改动（计划外）

**A1 — `SSEWriter` 流前归属预检（`conversation_service.AssertAccessible`）**

实测发现：`POST /conversations/:id/messages` 越权返回的是 **200 而不是 404**。

根因：`NewSSEWriter` 之后一旦写出第一个事件，响应状态就固定为 200；越权错误只能退化成流内的 `error` 事件。任何只看状态码的客户端都会把越权失败误判为成功。

修法：在创建 SSE writer **之前**做一次归属预检（`AssertAccessible`），失败直接返回 404 JSON。安全上不依赖它——`AddMessage` / `GetMessages` 内部仍各自校验归属，预检只是让状态码正确。

**A2 — SSE 错误事件改为 JSON 转义（`handler.toJSONString`）**

原实现是 `` `{"error": "`+err.Error()+`"}` ``。新增的错误文案带括号和中文标点，一旦含引号/反斜杠就会拼出非法 JSON，前端 `JSON.parse` 失败后只看到一个语焉不详的「请求失败」。统一改走 `encoding/json` 转义。

**A3 — 启动日志不再打印引导口令**

原计划的 dev 启动日志会打印 `admin / 123456` 之类的提示。但 `BOOTSTRAP_ADMIN_PASSWORD` 在 dev 也可能被改成自定义值，打进日志等于把口令落到日志文件。改为只打印运行模式。

**A4 — `PrepareReading` 同时写入 `conversation_id`**

`StreamTarotReading` 与 `draw_tarot` 都传真实会话 id，使新数据不再依赖 `session_id = 'conv_<id>'` 这个字符串约定。

### 13.3 刻意未实现的东西

- **`auth.SystemActor()`**：一度实现为「绕过全部归属过滤」的便利函数，确认无调用方后**删除**。
  这类 API 一旦存在，迟早会有人在业务代码里顺手用它绕开隔离。确实需要跨用户查询时，
  走 `Actor{All: true}` 并在调用点写明理由。
- **`middleware.RequireAdmin()`**：只服务于本期的非目标 `/api/v1/admin/*`，
  与其留一个无人调用的中间件，不如等真正实现管理界面时再写。

### 13.4 实测数据（与原计划的差异）

| 项 | 原计划预估 | 实测 |
|---|---|---|
| bcrypt cost 12 单次耗时 | ~250ms | **~213ms** |
| 结构非法的 bcrypt 哈希耗时 | 未考虑 | **~120ns**（比合法哈希快 6 个数量级）。这正是 `auth.dummyHash` 必须用**合法**哈希的原因，否则反而把「用户是否存在」暴露得更彻底 |
| 登录锁定触发点 | 「连续 5 次失败锁定」 | 第 1–5 次返回 401，**第 6 次起返回 429**。实现是「失败 5 次后置锁定」，与描述一致，但边界上比「第 5 次就 429」晚一次 |
| 迁移回填 | 45 行可关联 + 15 行孤儿 | **完全一致**：45 行关联到会话，15 行归 admin |

### 13.5 实施中发现的既有问题（未修，不在本次范围）

**E1 — `GET /api/v1/cards/` 经 Next 代理会 301 自跳转**

现象：直连后端 `GET /api/v1/cards/` 返回 200（22 张牌）；但经 `localhost:3000/api/v1/cards/` 返回 301，`location` 指向同一个 URL，形成自跳转。

原因：`frontend/next.config.js:5` 的 `skipTrailingSlashRedirect: true` 与 gin 路由 `/cards/` 带尾斜杠的交互。`/cards/random/` 同样受影响。

与本次改造无关（`next.config.js` 与 `handler/card.go` 均未修改）。目前前端未直接调用这两个带尾斜杠的路径，所以未暴露。若后续要用，建议把 gin 路由的尾斜杠去掉。

### 13.6 环境注意事项（踩到的坑）

1. **`/tmp` 在 bash 工具调用之间不保留**（每次调用是独立沙箱）。迁移前备份必须落在工作区内，本次放在 `backend-go/backup/`（已加入 `.gitignore`）。
2. **Go 的 `GOCACHE` / `GOMODCACHE` 在工作区外**，沙箱下不可写。构建需显式指定 `GOCACHE=<工作区>/.gocache`。
3. **`config.Load()` 里的 `godotenv.Overload()` 会让 `.env` 覆盖 shell 环境变量**。想用临时环境变量（如 `APP_ENV=prod`、`MYSQL_DB=...`）跑测试，只有 `.env` 中**不存在**的键才生效。生产保护验收脚本（`backend-go/backup/prod_guard_test.sh`）因此需要临时改 `.env` 的 `MYSQL_DB`。
4. **`go run` 的子进程不会随父进程退出**。用 `pkill -f "cmd/server/main.go"` 杀掉父进程后，编译产物仍在监听端口，导致后续启动报 `address already in use`。注意 `pkill -f` 的模式会匹配到执行它的 shell 自身（命令行含同样字符串），需要更精确的模式。
5. **`go run` 每次重启都要重新编译**（~7s），验收时给足等待时间。
