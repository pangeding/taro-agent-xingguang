## 0. 结论摘要

占卜页 `/` 是**停留在旧接口、且大量使用假数据的历史遗留页面**，而 `/chat` 页已经是「SSE 流式 + conversations 持久化」的新架构。两者不是视觉代差，是**两代架构并存**。

用户感知到的「老 / 不舒服」，根因按影响排序：

| # | 根因 | 性质 |
|---|---|---|
| 1 | 占卜走阻塞式 `POST /readings/`，三张牌阵串行 3 次 LLM，全程只转圈、无进度、无超时 | 体验 |
| 2 | `ReadingHistory` 是写死的假数据，「刷新 / 查看 / 删除」全是假的 | 功能（欺骗性） |
| 3 | `TarotCard` 的「刷新解读」会把 AI 真实解读**替换成字面量占位符** | 数据破坏性 Bug |
| 4 | 「牌面含义」是模板套话，数据库里现成的真实牌义完全没用 | 功能 |
| 5 | 硬编码 `http://localhost:8000` 绝对地址，绕过 Next rewrite，cookie 身份丢失 | 工程 |
| 6 | 暗色模式下白字白底，页面基本不可读 | 视觉 Bug |
| 7 | 导航 5 条链接中 3 条是 `href="#"`，移动端导航整体隐藏且无汉堡菜单 | UX |
| 8 | 无牌面图、无翻牌动画、无发牌动效，纯静态卡片堆叠 | 视觉 |

**推荐路径**：P0 消除假数据与破坏性 Bug（纯前端 + 1 处后端小改）→ P1 迁移到 SSE 流式并复用 conversations 持久化（**历史记录零后端新增**）→ P2 视觉重做与全链路流式。

### 1.3 逐条问题与行号证据

#### A1. 硬编码绝对地址，绕过 rewrite 与身份 cookie

`frontend/app/page.jsx:28`

```js
const response = await axios.post('http://localhost:8000/api/v1/readings/', {...})
```

- `frontend/next.config.js:6-13` 已配置 `/api/:path*` → `http://localhost:8000/api/:path*` 的 rewrite，此处**未使用**。
- 对比 `frontend/app/chat/page.jsx:7`：`const API_BASE = process.env.NEXT_PUBLIC_API_URL || '/api/v1'`，且 `chat/page.jsx:117` 统一带 `credentials: 'same-origin'`。
- 影响：跨域请求 axios 默认不带 cookie → 后端 `middleware.UserID()`（`internal/middleware/user.go:16-21`）读不到 `user_id` cookie → 无法与 users/conversations 归属关联；部署到非 localhost 即整体失效。
- 注：`POST /readings/` 本身不读 user_id，故当前**尚不表现为报错**，但它是 P1 历史功能的必要前提。

#### A2. `ReadingHistory` 全部是假数据

`frontend/components/ReadingHistory.jsx:17-44`：

```js
await new Promise(resolve => setTimeout(resolve, 500))   // 假装在请求
setReadings([                                             // 写死两条 2024-01-15 的记录
  { id: 1, question: '工作发展前景如何？', ... },
  { id: 2, question: '感情关系的未来走向', ... },
])
```

- `handleViewReading`（第 56-59 行）只 `console.log`。
- `handleDeleteReading`（第 61-64 行）只对本地数组 `filter`，刷新即复活。
- 组件在 `page.jsx:261` 以 `sessionId={sessionId}` 挂载，而 `sessionId` 初值为 `null`（`page.jsx:14`），因此**首次进入必定显示「开始你的第一次占卜」空态**；只有完成一次占卜后才渲染那两条假记录。

#### A3. 「刷新解读」是数据破坏性 Bug

`frontend/components/TarotCard.jsx:44-55`：

```js
const handleRefresh = async () => {
  setIsLoading(true)
  await new Promise(resolve => setTimeout(resolve, 1000))
  setInterpretation('新的解读内容...')   // ← 把 AI 真实解读覆盖为字面量
}
```

用户点击一次，AI 生成的解读即被永久替换为字符串 `新的解读内容...`（仅前端 state，刷新页面可恢复）。

#### A4. 「牌面含义」是模板套话，真实牌义未被使用

`frontend/components/TarotCard.jsx:110-121`：文案为 `card.is_reversed ? '逆位表示挑战、阻碍或需要反思的方面' : '正位表示机遇、积极的发展方向'`，与具体是哪张牌无关。

数据侧：`db.TarotCard`（`internal/db/models.go:7-19`）具备 `MeaningUpright / MeaningReversed / Keywords / Element / ZodiacSign / Description / ImageURL`，`data/tarot_cards.json` 已填充（22 张大阿卡纳），`GET /api/v1/cards/:id` 也已返回（`internal/service/card_service.go:31-45` 的 `CardDetail`）。

但占卜结果的出参 `ReadingCardResponse`（`internal/service/reading_service.go:22-29`）**只返回 6 个字段**：

```go
CardID, Name, Position, IsReversed, Interpretation, ImageURL
```

故前端拿不到牌义。这是一个**后端出参缺字段**问题，不是前端偷懒。

#### A5. 位置语义靠显示文案判断

`frontend/components/TarotCard.jsx:13-18` 的 `positionDescriptions` 只覆盖 `single`/`three`；`TarotCard.jsx:117-119` 用三元表达式 `positionName === '过去' ? '已经经历' : positionName === '现在' ? '正在面对' : '将要面对'`——把**用于展示的字符串**当作**逻辑判断依据**，扩散牌阵或改文案即静默错位。

#### A6. 「AI正在深度解读中…」是恒真文案 + 无进度 + 无超时

- `frontend/app/page.jsx:206-218`：该蓝色提示块**无条件渲染**，只要 `currentReading` 存在就显示，与是否真的在解读无关。实际上 `POST /readings/` 是**同步返回**（`internal/service/reading_service.go:132-147` 逐张牌顺序调用 `s.LLM.Chat`，写完才返回），响应到达时解读已经就绪。
- 提交按钮 `page.jsx:159-172` 只显示一个转圈 + 「正在连接AI进行占卜...」；三张牌阵 = 3 次串行 LLM 调用，实测需数十秒，**期间无任何阶段性反馈**。
- axios 未设 `timeout`（默认 0 = 永不超时），后端卡死则前端永久转圈。
- `page.jsx:37-41` 的 catch 把后端错误统一吞成「占卜失败，请稍后重试」，丢失 `err.response.data.error`。

#### A7. 解读中的 Markdown 不渲染

`page.jsx:194-201` → `TarotCard.jsx:143-145` 用 `<p className="... whitespace-pre-line">{interpretation}</p>` 原样输出。

而后端三张牌阵会追加综合解读（`internal/service/reading_service.go:235-241`）：

```go
lastRC.Interpretation += "\n\n---\n**综合解读**: " + state.Synthesis
```

`**综合解读**` 与 `---` 会以**裸文本**显示。

聊天页已有可复用的 `SimpleMarkdown`（`frontend/app/chat/page.jsx:9-47`），手写了 `**粗体**` / `*斜体*` / `` `code` `` / `#`~`###` / ``` 围栏 ``` 的解析。

#### A8. `sessionId` 不持久化

`frontend/app/page.jsx:14` 的 `sessionId` 仅存于 React state，刷新即丢，无 localStorage。对比 chat 页用后端 `conversations` 表持久化（`chat/page.jsx:127-142`）。

#### A9. 牌面图未使用

`TarotCard.jsx:64-79` 用一个显示序号的方块（`w-12 h-16`）代替牌面图，`card.image_url` 被完全忽略。注意 `data/tarot_cards.json` 中 `image_url` **全部为 `null`**，因此启用真实牌面图需先补图源（见 §5.3）。

#### A10. 用的是"旧"接口，"新"接口更好且已在别处使用

`page.jsx:28` 打 `POST /readings/`，而项目已有 `POST /api/v1/conversations/:id/tarot`（`internal/service/conversation_service.go:249-338`），其事件契约如下：

```
event: card_drawn   data: {"name":"愚人","is_reversed":false,"position":0}   每张牌一次，立即推送
event: message      data: {"delta":"…"}                                      逐字流式
event: done         data: {"done":true,"full_text":"…","reading_id":12,"msg_id":34}
event: error        data: {"error":"…"}
```

前端解析逻辑已在 `frontend/app/chat/page.jsx:260-316` 实现（含 `\n\n` 分块、`event:`/`data:` 行解析、`AbortController` 取消）。

> 注意一个后端时序细节：`StreamTarotReading` 在推完 `card_drawn` 后，**仍会阻塞执行** `CreateReadingLangGraph` / `CreateReading`（`conversation_service.go:282-291`）逐张牌解读，之后才开始流式输出综合解读。即：**牌面可以立即翻出，但逐张牌解读目前拿不到流式**。要全链路流式需改后端，见 §5.2。

const handleRefresh = async () => {
  if (!readingId) return
  setIsLoading(true)
  try {
    const res = await axios.get(`${API_BASE}/readings/${readingId}`, {
      timeout: 30000,
      withCredentials: true,
    })
    const fresh = res.data?.cards?.find(

  }
}

## 8. 执行中额外发现的两个缺陷（均已修复）

这两项**不在原计划内**，但都是「不修则 P1 交付物不成立」的硬缺陷，故一并修复。

### 8.1 【阻断级】Next.js 的 gzip 压缩会把 SSE 整个缓冲到结束才下发

**这正是「流式像假的」的真正原因，也是原计划完全没有预料到的。**

**现象**：前端 `streamSSE` 在浏览器里拿不到任何中间分片——整条响应作为一个 chunk 在结束时一次性到达。

**定位过程与证据**：

| 测试 | 首块到达 | 结论 |
|---|---|---|
| 浏览器 fetch 经 `:3000` rewrite | `+15841ms`，单个 12610B chunk | 全缓冲 |
| 浏览器 fetch 直连 `:8000` | `+9ms`，50B（正好是一个 `card_drawn` 事件） | 后端正常流式 |
| `curl -N` 经 `:3000`，**不带** `Accept-Encoding` | `card_drawn +0.03s`，末事件 `+6.27s` | 「看起来正常」← **误导项** |
| `curl -N --compressed` 经 `:3000`（等同浏览器） | 131 个事件**全部**在 `+5.17s` 同刻到达 | **确认被 gzip 缓冲** |

**根因**：浏览器一定会发送 `Accept-Encoding: gzip`，Next.js 服务端（dev 与 `next start` 均是）会对经 rewrite 代理的 `text/event-stream` 响应启用 gzip；zlib 在流结束前不 flush，于是响应被整体缓冲。**只有不带该请求头的 curl 才会看到正常流式——这是排查时最容易走错的一步。**

**影响面**：`/chat` 页一直宣称的「逐字流式回复」**在浏览器里从未生效过**，用户实际体验与阻塞式请求无异。也就是说这个问题同时压着新旧两个页面。

**修复**：`frontend/next.config.js` 增加 `compress: false`（附注释说明原因）。

**代价（需知悉）**：Next 不再 gzip 任何响应，包括 JS/CSS/HTML。本地开发无影响；生产部署应由 nginx/CDN 承担压缩。若将来必须让 Next 自己压缩，则需改为**不在 SSE 路径走 Next 代理**（例如把 `NEXT_PUBLIC_API_URL` 指向后端直连，后端 CORS 已默认放行 `http://localhost:3000`）。

**验证**：`compress: false` 后，dev 与 `next start` 生产模式下带 gzip 头的 SSE 均为 `首个事件 +0.03s / 末个事件 +5.98s`。

### 8.2 【正确性】`card_drawn` 推送的牌与实际解读的牌不是同一副

**现象**：SSE 在 `+0.1s` 推送 `{"name":"愚人","is_reversed":false}`，而随后流出的解读文本通篇在讲**「高塔」逆位**。

**根因**：`internal/service/conversation_service.go` 的 `StreamTarotReading` 里抽了两次牌：

```go
drawnCards, err := readingSvc.DrawCards(count)      // 第 269 行：抽第一副，推给前端
for i, dc := range drawnCards { writer("card_drawn", ...) }

readingResult, err = readingSvc.CreateReading(question, spreadType, sid)  // 第 287 行
//                        ↑ CreateReading 内部又调用了一次 DrawCards，抽了第二副
```

`CreateReading` / `CreateReadingLangGraph` 原本都在函数体内自行抽牌，于是「推送的牌」与「解读的牌」是两个独立随机结果。

**影响面**：同样波及 `/chat`——聊天页的 `CardStrip` 显示的牌与解读内容一直对不上；且卡片带 `reading_id` 存入数据库，导致占卜记录自相矛盾。

**修复**：把抽牌与解读解耦，新增两个接收「已抽好的牌」的入口，原函数退化为「先抽再调」的薄包装：

```go
// internal/service/reading_service.go
func (s *ReadingService) CreateReadingWithCards(question, spreadType string, sessionID *string, drawnCards []DrawnCard) (*ReadingResult, error)
func (s *ReadingService) CreateReadingLangGraphWithCards(question, spreadType string, sessionID, modelName *string, drawnCards []DrawnCard) (*ReadingResult, error)
```

`CreateReading` / `CreateReadingLangGraph` 内部改为 `DrawCards` 后转调上述函数；`StreamTarotReading` 改为传入第 269 行已推送的那副牌。既有调用方（HTTP handler、WebSocket、`tarot_tool.go`）签名不变。

**验证**：single 与 three 两种牌阵各跑一次，`card_drawn` 推送序列与 `GET /readings/:id` 落库结果**逐张一致**（含正逆位与位置）。

### 9.4 遗留观察（未处理，供决策）

1. **三张牌阵仍要等 ~30 秒**：`StreamTarotReading` 在推完 `card_drawn` 后仍阻塞执行逐张解读（`conversation_service.go:282-291`），之后才流式输出综合解读。牌面秒出，但文字要等。彻底解决需 §5.2 的 `card_interpreted` 事件。
2. **综合解读会提到未抽到的牌**：模型在综合叙述时带出了 `力量`、`世界` 等未抽中的牌名。根因是 `TAROT_READING_SYSTEM_PROMPT` 未像 `CHAT_SYSTEM_PROMPT` 那样明确禁止提及牌库中的其他牌，且逐张解读文本里已有类比性提及，被一并喂进了综合 prompt。属 prompt 调优，本轮未改动以免改变输出风格。
3. **`ReadingHistory` 的删除按钮删的是整个会话**（后端没有单条占卜的删除接口），已在 `window.confirm` 文案中明确说明会连带删除该对话的聊天消息。
4. **`compress: false` 的静态资源压缩代价**（见 §8.1）。
5. `frontend/jsconfig.json` 未新增（未采用 `@/` 别名，改用相对路径，避免引入配置）。
